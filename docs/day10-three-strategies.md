# День 10: три стратегии управления контекстом

Реализованы три стратегии без rolling summary. Стратегия **выбирается один раз** при создании диалога (экран «Новый диалог») и **не меняется** во время общения.

## Стратегии

| Стратегия | Что уходит в API | Что видит пользователь |
|-----------|------------------|------------------------|
| **Sliding Window** | system + последние 8 реплик | полная лента |
| **Sticky Facts** | system + блок facts (KV) + последние 8 реплик | полная лента + превью фактов |
| **Branching** | system + trunk (до checkpoint) + хвост активной ветки (до 8) | trunk + активная ветка; переключение A/B |

## Как проверить

1. Запустите приложение (`./gradlew :desktopApp:run` или Android).
2. «Новая тема» → выберите стратегию → «Начать диалог».
3. Прогоните **один сценарий** (10–15 сообщений) на каждой стратегии.

### Сценарий: сбор ТЗ мобильного приложения

1. «Нужно ТЗ на приложение доставки еды. Задай уточняющие вопросы.»
2. «Целевая аудитория — города 100k+, возраст 20–35.»
3. «Платформы: iOS и Android, MVP за 3 месяца.»
4. «Бюджет разработки до 2 млн ₽.»
5. «Обязательно: каталог, корзина, оплата картой, push о статусе заказа.»
6. «Не нужны: чат с курьером, подписки, B2B.»
7. «Дизайн — светлая тема, акцент #FF6B35.»
8. «Админка для ресторанов — веб, отдельная команда.»
9. «Интеграция с CloudPayments.»
10. «Аналитика: Firebase + Amplitude.»
11. «Юридически: оферта, согласие на ПДн.»
12. «Приоритет №1 — скорость checkout, не больше 3 экранов.»
13. «Сформулируй итоговое ТЗ списком разделов.»

**Branching (дополнительно):** после 6–7 сообщений нажмите «Разветвить». В **ветке A**: «Приоритет — скорость checkout». В **ветке B**: «Приоритет — рекомендации и персонализация». Продолжите обе ветки и сравните итоговые ТЗ.

## Сравнение (шаблон)

| Критерий | Sliding Window | Sticky Facts | Branching |
|----------|----------------|--------------|-----------|
| **Качество ответа** | Хорошо на коротких диалогах; к 12–15 сообщению может «забыть» ранние ограничения | Стабильнее держит цель, бюджет, «не нужны» в блоке facts | Две независимые линии решений от одной точки |
| **Стабильность деталей** | Низкая после окна (8 msg) | Высокая для зафиксированных фактов | Trunk сохраняет общий контекст; ветки не смешиваются |
| **Расход токенов (prompt)** | Минимальный, ~константа | Чуть выше (facts + окно) | Trunk растёт + окно ветки; при длинном trunk — дороже sliding |
| **UX** | Простейший | Прозрачный блок «Факты» | Кнопка «Разветвить», переключатель A/B |

Смотрите **«Контекст последнего запроса»** в сводке диалога и **«≈ если бы вся лента была в промпте»** (для sliding/facts).

## Файлы

- `ContextStrategy.kt` — enum стратегий
- `SimpleAgent.kt` — логика окна, facts, branching для API
- `BranchingState.kt`, `BranchingJson.kt` — checkpoint и persist веток
- `NewChatScreen.kt` — выбор стратегии при старте
- `ChatScreen.kt` — read-only метка стратегии, UI веток

## Ожидаемое поведение

- **Sliding:** на шаге 13 модель может не упомянуть бюджет или «не нужны B2B», если они выпали из окна.
- **Facts:** в сводке появятся ключи вроде `бюджет`, `не_включать`, `платформы`; итоговое ТЗ их учитывает.
- **Branching:** итоги в A и B различаются по приоритету, общая часть (аудитория, платформы) одинакова из trunk.
